# FluentOps 企业级打磨路线图

更新时间：2026-03-22

## 1. 规划目标

本路线图的目标不是再做一轮“演示级增强”，而是把当前仓库推进到以下状态：

- 本地、WSL、CI 至少有一条明确且稳定的全链路开发路径。
- 前端、后端、存储、支付、AI、通知等核心流程都可重复验证。
- 代码、测试、部署、监控、文档、运维具备企业项目的基本可交付性。
- 每次新对话只做一个“叶子任务”，保证在单轮 200k 上下文内能完成、验证并落文档。

## 2. 本次实际查看后的基线结论

### 2.1 仓库结构

- Monorepo：`pnpm + turbo`
- 前端：`apps/web`，Vue 3 + Vite + Pinia + Vue Router + Element Plus + Tailwind
- 后端：`apps/api-gateway`，NestJS + Prisma + JWT + Redis + MinIO + WebSocket/SSE
- 共享包：`packages/shared`
- 基础设施：`infra/docker-compose.yml`
- 文档：`README*`、`docs/api-reference.md`、`docs/audit-report.md`

### 2.2 代码规模粗看

- `apps/api-gateway/src` 约 2702 行 TypeScript
- `apps/api-gateway/test` 约 1109 行 e2e / 测试支撑
- `apps/web/src/pages` 约 1508 行页面代码
- `packages/shared/src` 约 90 行

### 2.3 实测结果

- 根级 `lint`：通过
- 根级 `typecheck`：通过
- `api-gateway` 单测：通过，5 个 suite，23 个测试
- `api-gateway` e2e：通过，1 个 suite，28 个测试
- 根级 `test`：通过（2026-03-22，3 个包全部通过，耗时约 2m42s）
- 根级 `build`：通过（2026-03-22，3 个包全部通过，耗时约 1m56s；仍有前端 chunk 体积警告）

### 2.4 当前最关键阻塞

当前最真实、最优先的阻塞不是业务代码本身，而是工作区通路不稳定：

- 当前环境为 WSL/Linux 运行项目，但仓库 `node_modules` 明显带有 Windows 安装痕迹。
- `web` 相关 `vitest/vite/rollup` 在 WSL 下缺少 `@rollup/rollup-linux-x64-gnu` 可选依赖。
- 结果是：
  - 后端链路基本可跑；
  - 根级测试和构建并不真正“全通”；
  - “企业级可用”的第一步必须先把环境和构建矩阵收敛。

### 2.5 当前已具备的强项

- 后端核心业务流已不是空壳：
  - 认证
  - 媒体上传
  - AI 评测
  - 积分计费
  - 通知发送
  - 实时推送
- 后端单测和 e2e 已有一定深度，说明 API 侧基础比前端更成熟。
- README、审计文档、安全文档、CI 已有雏形，不需要从零搭。

### 2.6 当前明显短板

- 前端测试覆盖极弱，现状基本只有 smoke test。
- 根级构建/测试的跨平台稳定性不足。
- 尚未看到面向生产的容器化交付、环境分层、观测性、告警、回滚、备份恢复体系。
- 刷新令牌仍走 `localStorage` 路径，离企业级安全基线还有距离。
- 仍缺少真正的发布流程与运行手册。

## 3. 执行规则

### 3.1 单轮对话规则

后续每次开新对话，严格只做一个“叶子任务”。

叶子任务必须满足：

- 目标单一
- 影响面有限
- 能写代码
- 能验证
- 能更新文档
- 不跨两个以上大工作流

### 3.2 完成定义

每个叶子任务都必须同时满足：

1. 代码或配置已落地
2. 至少有一条验证命令或人工验证路径
3. 若改变了使用方式，必须同步更新文档
4. 若暴露新风险，必须在文档中记录

### 3.3 执行顺序

优先级必须按下面顺序推进：

1. 先恢复工作区和根级通路
2. 再补强前端与全栈用户流程
3. 再做安全、运维、发布、治理
